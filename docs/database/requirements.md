# 星漫云数据库需求分析

## 1. 项目范围

星漫云面向动漫内容的浏览、制作信息管理、播放平台维护和用户互动。数据库必须同时支撑普通用户、管理员和数据库课程实验三类场景。

普通用户可以注册、登录、浏览动漫、搜索筛选、查看详情/剧集/制作人员/平台、收藏、取消收藏、记录观看进度、发表和修改评论、维护个人资料。

管理员可以维护动漫、制作厂商、类型、剧集、制作人员、播放平台、用户、角色、评论和操作日志，并查看统计结果。数据库实验室可以真实读取视图、调用过程、观察触发器计数和演示事务提交/回滚。

## 2. 数据边界

| 数据域 | 主要表 | 业务职责 |
|---|---|---|
| 身份与权限 | `sys_user`, `sys_role`, `sys_user_role` | 登录凭据、RBAC 角色、多对多授权 |
| 个人资料 | `sys_user_profile` | 用户一对一扩展资料和偏好 |
| 内容主数据 | `anime_studio`, `anime`, `anime_genre` | 厂商、作品、类型字典 |
| 内容关系 | `anime_genre_relation`, `anime_episode`, `anime_staff`, `anime_staff_relation`, `streaming_platform`, `anime_platform_relation` | 多对多分类、剧集、制作人员、平台发行 |
| 用户互动 | `user_favorite`, `user_watch_history`, `anime_review` | 收藏、观看进度、评论 |
| 审计 | `operation_log` | 管理动作、事务演示与安全追踪 |

共 17 张业务表：用户指定的 16 张核心表，加上为实现严格一对一关系和个人偏好而增加的 `sys_user_profile`，没有为数量添加无业务意义表。

## 3. 主要业务规则

1. 用户名、邮箱、角色代码、制作厂商名称、类型名称/别名、平台名称/代码唯一。
2. 一部动漫必须属于一个制作厂商；厂商被引用时不能直接删除。
3. 一部动漫可以对应多个类型、多个制作人员和多个播放平台，均通过关系表拆分。
4. 同一动漫的集数编号唯一，同一用户对同一动漫最多一条评论，对同一动漫最多一条收藏。
5. 同一用户对同一剧集只保留一条最新观看进度。
6. 评论评分为 1 到 10；状态只允许可见/隐藏。
7. 动漫的收藏、评论、评分和观看计数必须与来源关系一致且非负。
8. 用户删除时清理其角色、资料、收藏、观看和评论；操作日志保留并把操作者置空。
9. 动漫删除时级联清理类型关系、剧集、制作关系、平台关系、收藏、观看和评论；厂商、类型、人员和平台主数据限制删除。
10. 所有密码只保存 BCrypt 哈希，不保存明文。

## 4. 关键查询需求

- 按标题模糊搜索，按类型、厂商、状态组合筛选。
- 动漫详情聚合厂商、类型、集数和互动统计。
- 厂商作品数、平均评分、收藏总量排行。
- 类型热度、平台覆盖、用户活跃度、评论趋势。
- 评分排名、加权热度排名、高于厂商平均分的作品。
- 无评论作品、至少有一个角色的用户、用户最近观看记录。
- 使用 CTE、窗口函数、`EXISTS`、`NOT EXISTS`、相关子查询和条件聚合。

## 5. 完整性需求

实体完整性由主键保证；域完整性由数据类型、非空、`CHECK` 和唯一约束保证；参照完整性由外键保证。触发器维护冗余聚合字段且应用侧只读，关系表主键和用户/动漫唯一键阻止重复业务记录。动漫标题使用函数唯一索引处理发行日期为 NULL 时的重复判断。

## 6. 安全需求

管理员只用于建库、授权和 DDL。应用账户 `Chengzi@localhost` 仅对 `anime_platform` 授予 `SELECT`、`INSERT`、`UPDATE`、`DELETE`、`EXECUTE`、`SHOW VIEW`。禁止全局权限、跨库授权、硬编码真实密码和 `DROP DATABASE` 自动化。
